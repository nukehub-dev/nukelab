| 2026-08-15 | Toolchain datasets under `/opt/nuke/data/<name>`; separate shared data volume deferred | OpenMC cross-sections/chain files move from `/opt/nuke/openmc_data` to `/opt/nuke/data/openmc`; Geant4 datasets stay under `/opt/nuke/geant4/share/data` (Geant4-native discovery via `geant4.sh`/compiled datadir). | 2026-08-21 | Git tags as the version source of truth; `scripts/bump-version.sh` + root `CHANGELOG.md`; `APP_VERSION` build arg everywhere | Versions were scattered (`frontend/package.json` at `0.0.0`, backend `2.0.0` hardcoded in three files) and no tags existed, so `ci-version.sh` never produced semver image tags. The bumper syncs `VERSION`, `frontend/package.json` (+lockfile), and the changelog. Runtime version is fully dynamic: `settings.app_version` resolves `APP_VERSION` env-first, injected as a build arg by CI (the image tag) and by compose builds (`NUKELAB_VERSION` exported by `nukelabctl`), so `backend/app/version.py` is a fixed `0.0.0-dev` sentinel that is never bumped. The changelog stays manual (Keep a Changelog, same format as nuke-ide) because the commit history does not follow conventional commits, which auto-generators require | Approved |
| 2026-08-21 | Pull-based production deploys implemented | `compose.yml` now declares `image:` references to the CI-built GHCR images for `backend`, `celery-worker`, `celery-beat`, and `frontend`. Pinning `NUKELAB_VERSION` or `NUKELAB_IMAGE_TAG` switches `nukelabctl start` / `update` to pull those tagged images instead of rebuilding from source; rollback = re-pin. Unpinned deploys keep the source-build path | Approved |
| 2026-11-15 | Transaction-owned admission and durable volume intents; approved immutable environment revisions; private offline recovery into new volumes | Fresh Read Committed accounting after separate lock acquisition avoids stale admission snapshots. Persist intent before runtime I/O, retain protection for uncertain executors, and require current authorization for recreation. Integrated application flows use these additive foundations; a combined runtime acceptance suite covers provenance, queued recreation and offline volume recovery | Implemented |
| 2026-11-16 | Shared fenced lifecycle journal and atomic owner queue transport | API, bulk/admin, schedule/health and runtime enforcement tasks use shared reservations and pinned generations. Unknown runtime outcomes retain protection; status observations check current authority under admission. Queue cancellation is enabled with the matching claim-aware worker. Mixed old/new workers are unsupported. `starting` requests are resolved from the linked operation, with an orphan cancelled only after runtime absence is proved | Implemented |
| 2026-11-17 | Saved provenance export and explicit approved recreation | History exports the recorded sanitized manifest, independent of mutable template edits or revocation. Source IDs are owner-only; imported JSON must match a current approved revision and explicit data bindings. Preview requires metadata read plus manage authorization and grants no lease. Approved artifacts are checked before admission; registry-verified revisions use exact platform digests and portable fingerprints | Implemented |
| 2026-11-18 | Offline private-volume recovery with a separate hardened helper and new-volume restores | Durable exclusion and verified termination protect source data; bounded local storage, retention pins and disabled-by-default capability keep operator prerequisites explicit. Execution heartbeats under the fenced row, and completion is applied only from artifact and helper-termination proof. Shared/live snapshots remain deferred | Implemented |
| 2026-11-19 | PostgreSQL 17 is the deployed runtime baseline | Compose, CI and the data-model documentation use `postgres:17-alpine`; the earlier PostgreSQL 18 note described an initial plan rather than the deployed stack. Update this row when the runtime major changes. | Approved |
| 2026-11-18 | Required frontend CI with disposable real-stack browser acceptance | Unit tests, Vite-only state tests, external browser flows, workspace/IDE gateway and the combined provenance/recovery scenario are required coverage before image publishing. The real stack uses the production build behind Traefik, local fixture runtime A/B images, a built helper and real runtime identity/hash assertions. Queue-admitted launches use the same worker hardening/auth/runtime configuration as the API. [CI workflow](../../.github/workflows/ci.yml) | Implemented |
| 2026-11-21 | Worker and operation heartbeats are inspection triggers, not takeover authority | Process-lifetime `worker_heartbeats` rows carry container incarnation, PID and single-process identity; active journal rows carry `executor_id`/`heartbeat_at`. A stale heartbeat only schedules inspection. A read-only classifier returns bounded evidence, and `operation_finalizer.py` is the sole mutation boundary under admission/row locks. Failure requires stopped liveness plus proved runtime absence; ambiguous evidence keeps `uncertain`/`recovery_required` protection. There is no TTL takeover or force path. | Implemented |
| 2026-11-21 | Registry-verified revisions and portable fingerprint matching | Verification resolves an approved reference to an exact platform manifest digest and proves the local artifact by canonical repository, platform and digest. `on_demand` may pull only that digest; `preload_only` fails closed. Portable fingerprints hash normalized configuration and verified platform identity, and cross-install manifests match active revisions by fingerprint only. Moving a tag requires explicit admin verify and never creates approval automatically. | Implemented |
| 2026-11-22 | Release-only deterministic SBOM and attestations alongside strict base-image pinning | External Dockerfile base images must be digest-pinned in the blocking Security Gate. A weekly scheduled review reports tag drift in one tracked issue without opening pull requests. Tagged releases generate a normalized CycloneDX SBOM from the published image digest, attest build provenance and the SBOM, and verify both in the Release workflow. This claims artifact provenance and inventory, not SLSA compliance. | Implemented |
| 2026-11-27 | Use the roadmap for product priorities and operational readiness | A short release baseline and open outcomes make planning gaps easy to find. The changelog records shipped changes by version, and GitHub Actions retains individual verification runs. | Implemented |
| 2026-11-28 | Keep batch jobs in a distinct `batch_jobs` journal rather than reusing `servers` | Jobs are single-run, headless, owner-scoped commands with no URL, IDE, health probe, or lifecycle actions. A separate journal keeps server semantics unchanged while sharing admission, quota, resource-pool accounting, and a `job_writer` volume guard | Implemented (pilot; submission disabled by default) |
| 2026-11-28 | Zero-cost batch-job pilot first, with paid settlement added behind a separate hold-based gate | Shipping the zero-cost path first avoided an unbounded charge while exercising selection, admission, runtime, logs, and recovery. Paid plans now sit behind `BATCH_JOBS_ALLOW_PAID_PLANS` and the job-scoped hold decision below, so the zero-cost path remains independently releasable | Superseded by the paid hold decision; zero-cost remains the default |
| 2026-11-28 | Paid batch jobs use a job-scoped credit hold with bounded settlement | A paid job reserves its maximum runtime cost at submission and charges only the observed interval at the frozen rate. Holds are created in the job transaction under the shared admission lock with the user row locked, and every debit path uses spendable balance so interactive usage cannot consume reserved credits. Queued cancel/expiry/pre-start failure refunds the full hold; terminal proof settles the unused authorization; `recovery_required` retains it. Settlement never blocks the terminal result and records unpaid debt instead of raising | Implemented (flag off by default; real paid job, integration, concurrency and migration suites passed; CI/staging pending) |
| 2026-11-28 | Docker-first hardened headless profile with `/work` preparation before the job | A batch command needs a writable owned volume but must not run as root or on the platform network. A bounded root prep container fixes only the selected `/work` volume, then the job runs as UID 65532 with a read-only rootfs, no capabilities, no network, no ports, and a timeout wrapper. A real Docker driver smoke passed; Podman enablement remains pending | Partial (Docker driver smoke passed; Podman pending) |
| 2026-11-28 | Make `job_writer` an exclusive `volume_operations` kind | File mutation, metadata/sharing changes, backup/restore, launch mount intent, and deletion must not race a running job's output volume. The existing partial unique guard extends to `job_writer`, and release still requires executor/termination proof | Implemented |
| 2026-11-28 | Expose a sanitized admin jobs surface with proof-only reconcile | Cross-owner visibility is useful for support and capacity review. Sanitized `/admin/jobs` shows state, ownership labels, reservation/guard flags, heartbeat and cleanup state; it never shows argv, logs, environment values, or runtime identity. A manage-permission action reruns the read-only classifier and applies only a proof-backed terminal outcome through the existing fenced finalizer; ambiguous evidence returns 409 and releases nothing. There is no force, retry, or manual release path; the later cross-owner jobs decision adds a reason-audited safe cancel | Implemented (proof-only reconcile; safe cancel added later) |
| 2026-11-28 | Physically purge expired job logs and send one owner completion notification | Read-time expiry alone leaves payload rows indefinitely, and silent completion leaves owners without a terminal signal. A bounded Beat purge removes only expired payloads while preserving the result and metadata. A terminal result sends one deduplicated in-app notification; delivery is best effort and never changes the result or releases protection | Implemented |
| 2026-11-28 | Report storage enforcement truthfully and allow fail-closed admission | A per-volume size limit is only real when the storage layer enforces it. A read-only XFS project-quota probe reports enforcement without mutation. `BATCH_JOBS_REQUIRE_STORAGE_ENFORCEMENT` defaults false for dev/test compatibility; when true, capabilities and submission fail closed and admission keeps jobs queued until the host probe passes | Implemented (over-cap XFS write still needs target-storage evidence) |
| 2026-11-28 | Guided first launch and read-only post-upgrade verification | Preselecting eligible current catalog defaults reduces first-launch mistakes, and surfacing stale saved defaults prevents submitting a removed plan/environment. `doctor --post-upgrade` gives operators a bounded read-only check of version, images, schema, workers, and recovery rows after a pinned upgrade. The staging upgrade/rollback rehearsal is still pending | Partial (implemented; staging rehearsal pending) |
| 2026-11-28 | Use plan-level availability instead of treating every CPU plan as a job plan | `server_plans.allow_servers` and `allow_batch_jobs` let admins create server-only, job-only, or shared plans in Admin → Plans. Jobs require an explicit `allow_batch_jobs` opt-in; server launch rejects job-only plans and the server catalog hides them. The shared hourly cost still distinguishes free and paid jobs, while `BATCH_JOBS_ALLOW_PAID_PLANS` remains the deployment-level paid-billing safety gate rather than a catalog control. Existing CPU plans are backfilled as job-enabled; new API-created plans opt in | Implemented |
| 2026-11-28 | Mirror the server cross-owner model for batch jobs and add reason-audited safe cancellation | `jobs:read_all`, `jobs:write_all`, and `jobs:access_others` replace the owner-only admin gate; `jobs:write_all` implies own-write plus read grants, and the Operations grants remain a compatibility fallback. Admin cancel shares the admission/row lock with submission: queued work becomes terminal and releases the full hold, started work records a stop request and keeps reservation/guard/hold until proof, and `recovery_required` stays reconcile-only. Every cancel is reason-audited atomically and notifies a foreign owner; there is still no retry, force, or manual release path | Implemented |
